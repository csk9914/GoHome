# Docs/Dev 리뷰 루프

`Docs/Dev/`의 개발용 문서(코드와 함께 바뀌는 문서군 — `Docs/Design/`·Notion과는 별개 체계, 자세한 경계는 저장소 루트 `CLAUDE.md` 참고)를 원칙급 리뷰어 서브에이전트로 반복 검증하고, 발견된 결함을 오케스트레이터(이 스킬을 실행하는 세션)가 직접 파일에 반영하는 절차다. 목표는 "리뷰 결과를 사람이 매번 판단해서 반영"하는 품질을 유지하면서도 페르소나·루프 종료 조건·중복 재보고 방지를 매번 새로 설계하지 않게 고정하는 것이다.

## 1. 대상과 루프 횟수 파싱

`$ARGUMENTS`에서 두 값을 파싱한다:
- **대상 파일**: 파일명 또는 별칭(`ARCHITECTURE`/`아키텍처` → `Docs/Dev/ARCHITECTURE.md`, `CONVENTIONS`/`컨벤션` → `Docs/Dev/CODING_CONVENTIONS.md`, `AI_AGENT_GUIDE`/`에이전트 가이드` → `Docs/Dev/AI_AGENT_GUIDE.md`). 복수 지정 가능(공백/쉼표 구분).
- **최대 루프 횟수**: 정수. 생략 시 기본값 3.

대상이 전혀 지정되지 않았으면 `AskUserQuestion`으로 아래 세 문서 중 무엇을 검토할지 묻는다(`multiSelect: true`):
- `ARCHITECTURE.md` — 시스템 간 클래스/인터페이스 매핑
- `CODING_CONVENTIONS.md` — C++ 코딩 표준, 폴더 규칙, C++/Blueprint 경계
- `AI_AGENT_GUIDE.md` — 팀원이 자기 AI 에이전트에게 담당 작업을 물어볼 때 따르는 절차

여러 문서가 선택되면 문서별로 아래 2~4단계를 독립적으로 수행한다 — 문서 간 편집 대상이 겹치지 않으므로, 여러 문서를 리뷰할 때는 문서별 루프를 **병렬(각 문서의 `Agent` 호출을 백그라운드로 동시에 시작)** 로 돌려 전체 소요 시간을 줄인다. 단, 같은 문서 안에서 회차(`i=1..N`)는 이전 회차의 반영 결과를 다음 회차가 검증해야 하므로 반드시 순차로 진행한다.

## 2. 문서별 리뷰어 페르소나

문서에 따라 서브에이전트에게 부여할 페르소나와 포커스 영역이 다르다. 반드시 아래 표를 따를 것 — 범용 "코드 리뷰어" 페르소나를 쓰지 않는다.

| 문서 | 페르소나 | 포커스 영역 |
|---|---|---|
| `ARCHITECTURE.md` | UE5.7 멀티플레이어 아키텍처 전문가 | Replication 정확성(권위/RepNotify/레이스), 소유권·생명주기(구독/재구독, 델리게이트 댕글링, 레벨 트래블), 인터페이스 경계의 실질적 디커플링 여부, 동시성 엣지 케이스, "결합도 절단" 결정이 2차 확장에도 버티는지, Day-1 병렬 착수 헤더 스텁 완결성, 클래스 다이어그램-본문 정합성 |
| `CODING_CONVENTIONS.md` | C++/UE 팀 코딩 표준 리뷰어 | 규칙이 실제로 강제/검증 가능한지(모호한 규칙 없음), 예외 케이스 누락, `ARCHITECTURE.md`의 폴더·클래스 명명과 모순되지 않는지, C++/Blueprint 경계 규정의 실행 가능성 |
| `AI_AGENT_GUIDE.md` | AI 에이전트 협업 워크플로 리뷰어 | 라우팅표가 가리키는 문서·앵커가 실제로 존재하는지, `ARCHITECTURE.md`/`CODING_CONVENTIONS.md`의 최신 절 구성과 어긋나지 않는지, [Docs/Design/DOC_MANAGEMENT.md 단일 출처 원칙](../../../Docs/Design/DOC_MANAGEMENT.md#단일-출처-원칙)과 모순되는 안내가 없는지 |

## 3. 리뷰→반영 루프

각 회차 `i = 1..N` (N = 최대 루프 횟수):

1. **이전 회차 요약 누적**: 1회차가 아니면, 지금까지 발견되어 반영한 항목들을 1~2문장씩 요약한 목록을 서브에이전트 프롬프트에 포함한다. "이미 고친 항목은 재보고하지 말고, 그 수정이 실제로 파일에 올바르게 반영되어 다른 절과 모순 없이 정합적인지만 검증하라"고 명시한다.
2. **서브에이전트 실행**: `Agent` 도구로 `general-purpose` 서브에이전트를 **`run_in_background: false`(동기)** 로 실행한다. 여러 문서를 동시에 리뷰 중이면, 이번 회차에 해당하는 각 문서의 `Agent` 호출을 같은 응답에서 한꺼번에(병렬로) 보낸다 — 개별 호출은 동기지만 서로 독립이므로 나란히 실행해 전체 대기 시간을 줄인다. 프롬프트에는 반드시:
   - 대상 파일의 절대 경로와, 서브에이전트가 스스로 전체를 Read하도록 지시(사전 요약을 신뢰하지 말 것)
   - 2단계에서 정한 페르소나와 포커스 영역
   - 사실관계 확인이 필요하면 `Docs/Design/`(01·02·03·05)이나 `Source/GoHome/`을 스스로 Grep/Read해서 검증하되, 문서 전체를 훑지 말고 리뷰 중인 주장과 직접 관련된 절/코드로 조회 범위를 좁히라는 지시 (예: "레벨 트래블이 실제로 일어나는가" 같은 주장은 추측하지 말고 근거 문서를 찾아 확인하되, 관련 없는 절까지 다 읽지 않는다)
   - 마지막 회차가 아니면 "Critical/Major/Minor 등급, 정확한 줄 번호, 구체적 수정안"을 요구. 마지막 회차(N번째)면 "Critical/Major만 보고하고 Minor는 생략"하도록 지시해 종료 판정을 명확히 한다.
   - 리뷰 끝에 "이 문서가 지금 상태로 실사용(Day-1 병렬 착수/실제 온보딩/실제 코딩) 준비가 됐는지" 한 줄 판정을 요구
3. **오케스트레이터의 검증 후 반영**: 서브에이전트 보고를 그대로 신뢰해 자동 적용하지 않는다. 각 finding에 대해:
   - Critical/Major는 근거를 재확인(필요하면 직접 Grep으로 관련 Design 문서·코드 대조)한 뒤 `Edit`로 직접 반영한다.
   - Minor는 오케스트레이터가 판단해 선택적으로 반영한다.
   - finding이 사실과 다르거나 이미 다른 방식으로 해결되어 있다면 반영하지 않고 그 이유를 사용자에게 남긴다.
4. **링크 검증**: 이번 회차에서 `Docs/Design/` 문서를 가리키는 앵커·헤더 텍스트를 건드렸다면 `node Docs/tools/check_doc_links.js`를 실행해 오류 0건을 확인한다(Docs/Design/DOC_MANAGEMENT.md의 수정 절차와 동일). `Docs/Dev/` 자체는 이 스크립트의 검증 대상이 아니므로, `Docs/Design/`으로 나가는 링크만 수동으로 다시 훑는다.
5. **종료 조건**: 이번 회차 리뷰가 Critical/Major 없이 "준비됨"으로 판정하면 루프를 즉시 중단한다(N회를 다 채울 필요 없음). 그렇지 않으면 다음 회차로 진행하고, N회에 도달하면 무조건 종료한다.

## 4. 단일 출처 원칙 안전장치

리뷰 중 `Docs/Design/`의 단일 출처 원칙(인일 추정치, 미션 가이드 충족 여부, 담당자/일정, 결정 색인)에 해당하는 내용을 새로 발견하거나 고쳐야 할 경우, **스킬이 자동으로 `03_GoHome_리스크_미결정사항.md`의 "결정 완료 색인"에 추가하지 않는다.** 대신 이런 항목을 발견했다고 사용자에게 보고하고, 반영 여부와 라벨(팀 결정/기획 수정/검증 추가)을 확인받는다.

## 5. 최종 요약

모든 문서·모든 회차가 끝나면 문서별로: 몇 회차를 돌았는지, 회차별로 무엇을 고쳤는지(Critical/Major 개수), 최종 판정(준비됨 / 루프 상한 도달 — 남은 항목 목록)을 간결히 보고한다. 개별 finding의 장황한 원문을 그대로 출력하지 않는다 — 한두 문장으로 압축.
