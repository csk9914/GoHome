## 1. 온라인 서브시스템 + 보이스

**스펙**: `OnlineSubsystemSteam`으로 세션 생성/참가, 호스트가 서버 겸임. 참가는 방 목록 선택 방식(커스텀 로비 UI 없음)이며, 참가 즉시 잠수정 내부 스폰(로비 겸용) — 호스트도 동일 지점. 보이스는 Steam 음성 API로 클라이언트 간 직접 처리. 재접속은 범위 제외.

같은 담당자가 게임 흐름 제어(GameState 상태 머신: 로비→**탐사 지역 선택**→출발→탐사→복귀→정산)와 도킹 문 개폐를 함께 구현. 도킹 문은 서버 권위로 개폐 상태를 리플리케이트하며, 열린 상태에서 몬스터가 진입 판정 범위에 들어오면 잠수정 위협 판정 → 실패 조건(기획서 2번) 반영.

> **기획 수정**: 탐사 지역(맵) 선택 상태를 GameState 상태 머신에 추가한다. 1차는 맵 1종(아틀란티스, → [7. 레벨](#7-레벨-그레이박스))뿐이라 확인 UI 수준으로 구현하되, 상태 머신은 맵 다종화를 전제로 확장 가능하게 설계한다.

> **검증 추가 (팀 결정)**: 미션 가이드 "제한 시간과 목표 점수 UI" 요건 중 제한 시간 타이머가 기존 문서에 시스템 배정이 없었다. **탐사 구간 제한 시간은 GameState에 서버 권위로 보유, 출발 시 카운트다운 시작, 0 도달 시 실패 조건(기획서 "탈출 실패 조건" 1번)으로 리플리케이트.** UI 표시는 6번(UI)에서 처리 (→ [6. UI](#6-ui)).

**복잡도/인일**: 중, 8~11인일 (게임 흐름 상태 머신 + 도킹 문 개폐 포함 상향).

**리스크**:
- 게임플레이보다 먼저 검증할 기반 인프라. 초반에 빈 레벨에서 세션 생성/입장부터 확인.
- 도킹 문 진입 판정은 5번(AI)과 좌표/트리거 조건을 맞춰야 하므로 사전 합의 필요. 트리거 조건 수치는 [01문서 1절](01_GoHome_기획서.md#1-steam-온라인-서브시스템--보이스)이 단일 출처.
- > **검증 추가 (결정됨)**: 대칭형 NAT 클라이언트는 Steam Relay(SDR) 자동 처리에 맡기기로 확정. 팀 테스트 시 서로 다른 네트워크 환경에서 최소 1회 접속 테스트 진행.

## 2. 이동 + 사운드

**스펙**: `CharacterMovementComponent` 확장 또는 부력 기반 커스텀 무브먼트. 서버 권위 처리 + 클라이언트 단순 보간, 예측/리컨실리에이션은 나중에. 이동 사운드는 AI 자극원으로 함께 등록.

> **기획 수정**: 환경 방해 요소 2번째 종류(수류 구간)는 2차로 이동했다. 1차 이동 시스템은 순수 이동+사운드만 담당한다. 수류 구간 스펙은 [13-3](#13-3-환경-방해-요소-2번째-종류-수류-구간)로 이전.

**복잡도/인일**: 중상, **9~14인일** (수류 구간 이관으로 하향, 기획 수정).

**리스크**:
- 호스트는 지연을 못 느끼므로 **비호스트 클라이언트 기준 테스트 필수**.
- 3·4·5번의 선행 조건이라 가장 먼저 착수(크리티컬 패스). 수류 구간이 빠지면서 4번 무게 인터페이스 스텁 대기 없이 즉시 착수 가능.

## 3. 산소 + HP

**스펙**: `UOxygenComponent`, `UHealthComponent`를 액터 컴포넌트로 구현. 무게는 `IWeightProvider`로 4번 시스템에서 참조. HP 0 도달 시 관전 모드로 전환. 수압 시스템은 제외.

**복잡도/인일**: 중, 5~7인일.

**리스크**: 무게 값을 참조하는 지점의 결합도를 인터페이스로 낮게 유지.

## 4. 상호작용, 운반, 납품

**스펙**: `IInteractable`로 상호작용 통일, 소유권 이전은 서버 RPC 요청 후 승인. 오른손 소켓 기준 통일(손전등만 왼손 예외). 집으면 오른손 소켓에 Attach 유지, 납품도 동일 상태에서 상호작용 처리. 물리 기반 홀딩 대신 소켓 어태치 사용(구현 단순, 리플리케이션 비용 낮음).

아이템은 액터 하나 + 데이터 애셋(무게/가치/파손 플래그/소음 플래그)으로 종 구분. 인벤토리는 4슬롯 배열, 사용 아이템도 동일 슬롯에서 1~4 키로 매핑(**슬롯별 개별 `RepNotify` 방식 확정**, 팀 결정 — 슬롯 단위 UI 갱신과 자연스럽게 맞물림). 손전등은 잠수정 스폰 지점에 기본 2개, 구매를 통한 추가 획득은 별도 이코노미 시스템(범위 제외).

> 아이템 초기값(무게/가치/소음 반경)은 [01문서 4절 표](01_GoHome_기획서.md#4-운반-아이템-3종) 참고 (검증 추가, 팀 결정 — 플레이테스트 전 작업값).

사망 시 소지 아이템은 드롭 후 서버가 월드 오브젝트로 전환, 생존 플레이어가 재획득 가능. 납품은 딜리버리 존 진입 시 서버가 가치 합산 후 제거.

2인 협동 운반은 1차 제외하되 확장 가능하게 설계. **2차에서 동시 트리거 게이트 방식으로 추가 확정** (→ [13](#13-2차-프로토타입-추가-시스템)). 물리적 공동 운반은 그 이후 스트레치로 유지.

**복잡도/인일**: 중상, 10~13인일.

**리스크**:
- 동시 픽업 레이스 컨디션에 서버 승인 우선순위 필요. 아이템 수치는 위 초기값으로 확정, 밸런스는 플레이테스트로 조정.
- 오른손 아이템 + 왼손 손전등 동시 사용 시 두 소켓의 애니메이션 블렌드 충돌 여부 점검 필요.
- 2인 협동 운반 확장 시 손전등 자동 수납 + 양손 상호작용 판정이 동시에 서버 승인을 거치는 구조 → 레이스 컨디션 검증 대상 추가.

## 5. AI 몬스터

**스펙**: 공통 기반(감지·상태 전이·이동)과 종별 고유 기믹을 분리하는 구조. 구현은 비헤이비어 트리 대신 `BP_Monster` 내부의 Enum 상태 머신(Patrol, Investigate, Chase, Attack, Return)과 Steering Behaviors(Seek, Arrive, Pursuit, Avoidance) — AI 담당자 기존 설계 준용. 소음 감지는 AI Perception 대신 자체 `GenerateNoise` 함수(위치·반경·타입·발생원) 재사용, 주변 몬스터와의 거리 확인 후 Investigate 전환. 종별 고유 기믹은 기반 상태 머신을 건드리지 않고 별도 컴포넌트로 붙였다 뗄 수 있는 구조.

1차 투입 종·소음 반경 확정치는 [01문서 5절](01_GoHome_기획서.md#5-ai-몬스터)이 단일 출처 — 팀원3(Abyss Quota) 원안 4종 중 GoHome 소음 시스템과 가장 자연스럽게 맞물리는 종을 선택했다.

**복잡도/인일**: 상, 15~19인일 (프레임워크 설계 및 1종 구현 기준 재추정).

**리스크**:
- AI 담당 소수 인원이 병목. 다른 시스템 완성을 기다리지 말고 소음 시스템 인터페이스부터 초반에 합의(위 반경 파라미터를 킥오프 1주차에 그대로 쓸지만 확인).

> **검증 추가**: 상세 구현 시 팀원3(Abyss Quota) 원본 문서(청각 추적자/빛 반응체/운반 방해자/돌진형 포식자 4종 정의, `ApplySteering` 합성 공식 등) 참조 — 함수명까지 동일.

> **검증 추가 — 성능 목표 확정 (팀 결정)**: 목표 60FPS 권장, 렌더링 비용이 큰 구간(AI 다수, 시야 이펙트)은 30FPS까지 허용(딥다이브 프로토콜 14번 기준 채택). 리슨 서버 구조상 호스트가 연산+렌더링을 동시 부담하므로, 1종 통합 직후 호스트 PC 기준으로 측정한다.

## 6. UI

**스펙**: UMG 기반, 각 시스템의 리플리케이티드 프로퍼티 바인딩. 산소/HP 게이지, 인벤토리(4슬롯 고정 그리드, 1~4번 키 입력과 슬롯 선택 바인딩), 납품 UI. **탐사 지역(맵) 선택 UI**(기획 수정, 1번 시스템 "탐사 지역 선택" 상태 대응 — 1차는 맵 1종뿐이라 확인 UI 수준). 잠수정 출발/복귀 로딩 연출 UI, 복귀 시 성공/실패 시각적 구분. **탐사 구간 제한 시간 카운트다운 UI**(1번 시스템 GameState 타이머 값 바인딩, 미션 가이드 "제한 시간과 목표 점수 UI" 요건의 절반 — 목표 점수 절반은 2차에서 추가, → [13-2](#13-2-목표-점수할당량-시스템)). 연출형 UI는 이 최소 범위를 넘지 않는다.

**복잡도/인일**: 중, 7~10인일 (로딩 연출 UI + 제한 시간 카운트다운 UI + 탐사 지역 선택 UI 포함, 모두 단순 텍스트/버튼 바인딩이라 기존 범위 내 흡수).

**리스크**:
- 2, 3, 4번이 안정화되기 전까지 완성 불가한 통합 작업. 프로퍼티 이름/타입을 초반에 합의.
- 성공/실패 로딩 연출은 기획서 2번(핵심 루프)의 실패 조건이 먼저 정의되어야 확정 가능.

## 7. 레벨 (그레이박스)

잠수정 + 시설 최소 테스트 레벨. 프로그래밍 인일 미포함, 담당과 착수 시점 별도 지정 필요. 도킹 문 개폐 메커닉은 1번 담당자가 구현하며, 레벨에는 물리적 배치와 개폐 애니메이션 지점만 반영하면 된다.

> "플레이어 상호 방해" 요건 충족 방식은 [01문서 3-7절](01_GoHome_기획서.md#7-플레이어-간-상호-방해--신규-시스템-없이-1차에-포함-검증-추가-팀-결정) 참고 — 레벨 설계 시 좁은 통로 최소 1곳 반영 필요.

> 1차 맵 컨셉은 [01문서 8-1절](01_GoHome_기획서.md#8-1-1차-프로토타입-맵--아틀란티스튜토리얼) 참고.
>
> 로비-탐사맵 흐름 변경(기획 수정)의 근거는 [01문서 2절](01_GoHome_기획서.md#2-핵심-루프)이 단일 출처 — 여기서는 레벨 구현 영향만 짚는다: 로비 씬과 탐사 씬을 분리해 이후 맵 추가에 대비한다.
>
> **향후 추가 예정 맵**(난파선, 침수된 심해 시설)과 설계 방향은 [01_GoHome_기획서.md 8절](01_GoHome_기획서.md#8-맵레벨-계획) 참고. 착수 시점·인일은 1차/2차 안정화 이후 별도 산정.

## 8. 장비 강화 시스템

**스펙**: 로비의 업그레이드 상호작용 지점에서 서버가 재화 차감과 스탯 적용을 처리. 무게 허용 한도 증가는 `IWeightProvider` 페널티 곡선 파라미터 조정, 최대 산소량 증가는 산소 컴포넌트 최대치 파라미터 조정으로 구현. 업그레이드 목록과 보유 재화는 9번 세이브 데이터 스키마에 포함.

**복잡도/인일**: 중, 5~7인일.

**리스크**: 재화가 파티 공유이므로 동시 구매 요청은 서버 권위 순차 처리 필요. **결정: 서버가 수신 순서대로 FIFO 처리, 처리 시점에 재화 부족하면 거부.** 별도 대기열/예약 시스템은 만들지 않는다.

## 9. 세이브 데이터 스키마

**스펙**: 자동 저장과 장비 강화가 추가되면서 필요해진 최소 스키마. 필드는 파티 공유 재화, 구매 완료 업그레이드 목록, 마지막 진행 지점으로 구성. 호스트 로컬 세이브(`SaveGame` 오브젝트)에 저장, 별도 백엔드 없음. 저장 시점은 로비 복귀 시점.

**복잡도/인일**: 하, 2~3인일.

**리스크**: 호스트 로컬에만 저장되므로 호스트 이탈 시 유실 위험 있음. 1·2차 모두 별도 백엔드 도입 없이 위험을 수용하고, 세션 시작 전 호스트 확인으로 완화한다 (팀 결정).

## 13. 2차 프로토타입 추가 시스템

> **검증 추가**: 이 세 항목(2인 협동 장치·목표 점수 시스템·환경 방해 요소 2번째 종류)은 미션 가이드 필수 요건이며 2차로 배정됐다. 1차 8개 시스템의 인일 합계(61~84인일)에는 포함되지 않은 별도 산정치다.

### 13-1. 2인 협동 장치 (동시 트리거 게이트)

**스펙**: 두 개의 독립된 `IInteractable` 트리거가 일정 시간 내 동시 활성화되는지 서버가 체크하는 액터 컴포넌트(가칭 `UMultiActorGateComponent`, 또는 도킹 문 컴포넌트 확장). 상태머신은 팀원3의 이중 레버 설계(Idle → Armed → Success/Failed → Open → Cooldown)를 단순화해 참고. 봉인 보관실 등 고가치 아이템을 지키는 구역에 배치해 위험-보상 구조와 연결.

**복잡도/인일**: 중하, 3~5인일 (1차 도킹 문 개폐 컴포넌트와 기반 공유 시 하한에 가까움).

**리스크**: 1번(멀티) 담당자가 이미 구현한 도킹 문 리플리케이션 패턴 재사용 여부에 따라 공수가 크게 갈린다. 1차 도킹 문 컴포넌트 설계 시 이 재사용 가능성을 염두에 두고 인터페이스를 짜두는 것을 권장.

### 13-2. 목표 점수(할당량) 시스템

**스펙**: GameState에 목표 점수 필드 추가, 정산 시 누적 점수와 비교해 성공/실패 판정에 반영. 세이브 스키마(9번)에 목표 점수 관련 필드 추가. UI(6번)에 목표 점수/현재 점수 표시 추가.

**복잡도/인일**: 하, 2~3인일 (기존 정산 로직에 비교 조건만 추가하는 수준).

**리스크**: 목표 점수 수치 자체가 밸런스 이슈이므로 아이템 가치 수치(→ [01문서 4절 표](01_GoHome_기획서.md#4-운반-아이템-3종)) 확정과 함께 조정 필요.

### 13-3. 환경 방해 요소 2번째 종류 (수류 구간)

**스펙**: `PhysicsVolume`(FluidFriction 또는 RadialForce/ZoneVelocity) 기반으로 방향력을 가하는 구역. 4번 시스템의 `IWeightProvider` 값을 참조해 무거울수록 더 크게 밀리게 한다. 팀원3/팀원4 원안 모두 저비용 구현으로 분류(팀원4 메모: "PhysicsVolume의 FluidFriction/ZoneVelocity로 대부분 커버"). 1차 아틀란티스 맵 또는 이후 맵의 좁은 통로 구간과 함께 배치하면 상승효과가 있다.

**복잡도/인일**: 하, 2~3인일 (`IWeightProvider`가 1차 시점에 이미 안정화되어 스텁 합의 없이 바로 참조 가능해 하한에 가까움).

**리스크**: 1차 이동 시스템(2번) 담당자의 기존 이동 로직에 얼마나 매끄럽게 얹을 수 있는지에 따라 공수가 갈린다. 배치 맵(1차 아틀란티스 재사용 vs 신규 맵)도 함께 결정 필요.
